- No maintenance tool pushes to main (2026-10-23). `publish-changes.mjs` (editorial decisions, study guides, subject order) and `update-collection.ps1` commit through a temporary Git index (the folder stays on main) and push a new `maintenance/<kind>-<timestamp>` branch, then open a pull request with a generated change summary (`describe-subject-order.mjs`, `describe-collection-update.py`, `describeGuideChanges`). Proposed files stay as local changes; the next run restores those that now match `origin/main` before fast-forwarding, and a file edited again after its earlier pull request was merged is three-way merged (`mergeLocalEdit`: base HEAD, GitHub's `origin/main`) so the new edit stays on top; only overlapping edits block (2026-10-28).
- `maintenance/Edit-Study-Guide.cmd` runs `scripts/edit-study-guide-server.mjs`: a local page that edits a guide's wording and reading order in `study-guides/*.json` (checks in `study-guide-store.mjs` mirror `build-compilation-pilot.mjs`; quotation previews come from the published site via `study-guide-quotations.mjs`). It never changes `selection`, `slug`, `id` or neighbor evidence.
- An order entry may carry `shortened` (verbatim whole-sentence spans, checked by `scripts/study-guide-shortening.mjs`) and `omitted: true` (left out of the published guide but still covered; never allowed for authorized wording). The editor's sentence picker and its save checks use `scripts/study-guide-passage.mjs`, which mirrors the build. Question limits count only the readings shown.
- `study-guides/` is not part of the deployment cache key: `deployment-cache.mjs refresh` rebuilds the guides on every deployment, so guide-only pushes reuse the cached collection.
- Edit-Catalog-Item (`scripts/edit-item-server.mjs`, `item-editor.html`, `catalog-edits.mjs`) never publishes or writes source files: Save records the edit (full metadata row and texts, plus the source `state` it was based on) in `.qa/pending-catalog-edits.json`; Mark for deletion records `{action:'delete'}`. Publish-Editorial-Decisions.cmd (`publish-editorial-decisions.mjs`) publishes every pending entry with the optional decisions export as one `maintenance/catalog-edits-*` pull request (`maintenance/editorial-decisions-*` when only decisions): `prepareCatalogProposal` reads the published shards and data files from `origin/main` through `git cat-file` (`publishedFiles`, no checkout), patches only the affected shards with `patch-item-archive.py --batch` (Python; `--inspect` reports the published state), plans deletions with `planDeletion`, and `proposalCommit(..., blobs)` commits the prepared files byte for byte (`hash-object --no-filters`). Text the editor left as the source folder has it (`unchanged` in the entry) keeps its published bytes, so its version stays even when that folder lacks or differs in the text; an English change that reviewed quotations refer to stays pending. After the pull request is open the edits are written to the local source folders with backups (`applyLocally`) and the entries stay marked `publishedIn` until the pull request is merged (`settlePullRequest`: closed → proposed again). One tool pull request at a time (`requireNoOpenProposals`; Update-Collection checks too). PDFs are untouched; `ItemStore.save` checks an item-level `state`, not the whole CSV.
- `.github/workflows/check-pull-request.yml` builds and tests every pull request with the deployment cache. When a `maintenance/catalog-edits-*` build stops with "Catalogue review data changed for …" (a deletion or correction moved quotations to other records), it runs `scripts/reconcile-study-guides.mjs` (the former `reconcileBuild`: `updateGuides` against the rebuilt dataset, before = live site), pushes the guide changes to the pull request branch, rebuilds, tests and comments on the pull request. `reconcileGuide` records `removedWithCatalogItems` once and takes a `cause` for its notes.
- Backups in `.qa/` are one ZIP each (2026-10-29): `ItemStore.replaceFiles` writes `.qa/item-backups/<stamp>.zip` (manifest.json plus previous bytes under their source paths) and `GuideStore.save` writes `.qa/guide-backups/<stamp>.zip` (`study-guides/<file>`), through `scripts/zip-archive.mjs` (no dependency). Dropbox syncs the folder, so file count matters. `maintenance/Tidy-QA-Folder.cmd` (`scripts/tidy-qa.mjs`) zips older backup folders and removes whole-project copies earlier tool versions left in `.qa/`, keeping any with changes or commits not on a remote.
- Volume view loads PDF.js after `src/map-polyfill.mjs` and uses `src/pdf-worker.mjs` as the worker entry; without them PDF.js 6 fails to render in browsers lacking `getOrInsertComputed`/`Math.sumPrecise`.

## Facts verified against the code (2026-11-03)
- Pending catalog edits live in `Downloads/subject-edits.json` under `catalogEdits` (`editorialFile`); `.qa/pending-catalog-edits.json` is only read as a legacy fallback. `PendingCatalogEdits.update` holds a lock in `%TEMP%\pi-browser-locks` so the editor and the publisher cannot overwrite each other; the publisher holds `%TEMP%\pi-browser-jobs\publish-editorial-decisions.lock` for the whole run (`withLock` in `publish-tools.mjs`, taken over when its process has ended). These machine-local locks replace the earlier rule that locks stay in `.qa/`.
- `ItemStore.applyBatch` writes all items of a publication at once: one read of the 17 MB metadata CSV, one rewrite that splices only the changed rows (`csvRecords`; values keep surrounding spaces, untouched rows keep their bytes), one backup ZIP, all files or none (`replaceFiles` rolls back). An edit is written only over the source state it was saved from (`state`, or `trimmedState` for entries saved before 2026-11-03, when metadata was trimmed). `save`/`remove` use it too.
- After `gh pr create` the publisher records the pull request in the pending file before writing the source folders; a later failure says the pull request was opened. On merge, `settlePullRequest` keeps entries whose local write failed or never happened. A failed `gh pr create` deletes the pushed branch.
- Exported subject decisions published once are recorded as digests (`publishedDecisions`, promoted from `pullRequest.decisions` on merge) and are not proposed again from an old export (`withoutPublished`).
- Speed: website files are downloaded once per run and in parallel (`liveSite` cache, `siteFiles`), Git blobs are read once (`publishedFiles` cache), `patch-item-archive.py --report` saves a Python pass, and the GitHub checks run alongside the fetch.
