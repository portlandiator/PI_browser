## Facts verified against the code (2026-11-12, build speed)
- Before this change a one-item catalog correction took about 29 minutes from publishing to the live site (#64): the pull request check and the deployment each rebuilt the whole collection (cache restore 1 s = miss, build 10 min, guides built again 3 min). A complete build is records and search index 1.5 min, subject matching 6 min, study guides 4 min.
- `deployment-cache.mjs` has three fingerprints: `fingerprint(root)` (every input; the cache key), `fingerprint(root,'records')` (builder code, root CSVs, PDFs, `data/withheld-pdf-volumes.json`, `data/volume-front-matter.json`) and `fingerprint(root,'subjects')` (everything except `data/collection/`). Both workflows restore the most recent cache (`pages-data-v3-<os>-`) and `build.mjs` decides: records are reused when the `records` fingerprint and the ID list match `build-state.json`; subjects are rebuilt when an English text changed or `state.subjectInputs` differs. The former `compatible` key hashed all of `data/`, which every catalog publication changes, so nothing was ever reused.
- `scripts/subject-match-cache.mjs` keeps each extract's match with what it depended on in `dist/subject-match-state.json.gz` (about 34 MB, 121,721 entries; excluded from the public site as "build cache only"; valid only for the same code closure of `build-subjects.mjs`). A match is reused unless: a supplied ID's text changed; a source it was found in changed; a changed text now contains its wording; or, for the 2,320 collection-wide approximate searches, a source it examined (`Matcher.examined`) changed or a changed text gained or lost one of its words (earlier wording read from the previous dataset's record, `previousCorpus`). `PI_INCREMENTAL=1` enables reuse; the Force full rebuild input sets it to 0.
- A subject rebuild inside an incremental build first removes the copied `subjects/` folder, so its files are those of a complete build.
- The build step applies the interface and builds the study guides itself, so the workflows run `deployment-cache.mjs refresh` only on an exact cache hit.
- Study-guide build: `read` caches up to 384 MB of records, `sentenceSpans` caches by text (callers get copies), neighbors with a guide reuse `subjectData`, `packGuideParagraphs` keeps every dictionary. Output is byte-identical (compared on all 659 guides); 276 s became 135 s.
- `scripts/verified-build.mjs`: the pull request check uploads `dist/` (without `pdf-volumes`) plus the two reports as artifact `verified-site-<git tree of HEAD>` after its tests pass (same-repository pull requests only, kept 5 days). The deployment (`actions: read`) looks for that name, accepts only an artifact of this repository's `check-pull-request.yml` run on a `pull_request` event, downloads it, runs `build-volumes.mjs` for the PDFs, runs the tests again, publishes and saves the cache. No artifact (pull request behind main, merged before the check ended, fork, Force full rebuild) means the normal incremental build.
- Verified on the real collection in a trial copy: after a one-word English edit the incremental build took 4 min 23 s (records 45 s, subjects 67 s with 4 of 121,721 extracts matched again, study guides 2 min 23 s) against 8.5 min complete; after an edit that inserts a paragraph into a quoted text 24 extracts were matched again. Both results equal a complete build of the same sources: all 59,773 collection files byte-identical except a few search shards whose JSON keys are in a different order (same data, as before this change), and all study-guide files identical apart from the dataset name and `editorialSha256` derived from it. The study guides are now the largest part of an incremental build; they are still rebuilt completely.
- Not yet run on GitHub: the artifact upload, lookup and download steps of the two workflows (they need a pull request and a merge). `verified-build.mjs find` falls back to a normal build on any error.
- If a build fails after subject matching (for example before guides are reconciled) and a text changes again before the next build, the saved matches are newer than the previous dataset's records, so the earlier wording is unavailable and the collection-wide approximate searches are repeated once (about 3.5 min).
- Experiments on a build need a separate copy of the project (hard links for the sources and PDFs, a real copy of `dist/`): the extracted source folders in the workspace are not to be edited either.

- No personal information and no analytics service. A page does nothing on load: after the visitor's first trusted `pointerdown`, `keydown`, `wheel` or `touchstart` in a visible page, or a `pointermove` that has travelled 8 px from where the pointer was first seen (never `scroll`, which a script can cause; and never one pointer event alone: headless Chromium gives the first page of a tab a trusted `pointermove` at 0,0 with nobody there, seen in 6 of 8 fresh browsers), a browser reads the counts from `api.github.com/repos/OWNER/REPO/releases/tags/visitor-counts` (unsigned, kept fifteen minutes in localStorage `pi-visitor-counts`; GitHub allows 60 an hour per address) and shows its page's. Once per page and UTC week (Monday start), at a further such action ten seconds or more after the first (see the ten-second rule below), it notes itself in `pi-visitor-week`, then requests `github.com/OWNER/REPO/releases/download/visitor-counts/<page>-<Monday>.gif` (`fetch` with `no-cors`, `credentials:'omit'`, `no-referrer`, `keepalive`). The file's `download_count` is the number shown. Owner and repository come from the module's own `https://OWNER.github.io/REPOSITORY/` address, so localhost, the iOS app's 127.0.0.1 and copies elsewhere do nothing. `navigator.webdriver` and crawler user agents are skipped, so a Playwright check must override both, move the mouse in steps (`page.mouse.move(x,y,{steps:6})`), press a key or tap, and do so again more than ten seconds later to be counted.
- The note is written before the request and never withdrawn. An earlier version withdrew it when the request failed and counted a visitor twice: a request cut short by leaving the page has often been counted already (reproduced 2026-11-13 with a delayed stand-in; with request interception Chromium rejects the request during `pagehide`, before later-registered `pagehide` listeners run). A browser that is offline, or cannot reach the API, is not noted and is counted on a later visit; a 404 (no release) is an answer and nothing is counted.
- `.github/workflows/visitor-counts.yml` (daily, pushes to main that touch its three files, manual; `contents: write`; sparse checkout of the two scripts) runs `scripts/visitor-counts.mjs`: creates the published `visitor-counts` release, adds one-pixel GIFs for this week and four ahead (never replaces one), rewrites the weekly table in the release notes (`readHistory`/`writeNotes`; a recorded count is never lowered) and removes files older than last week only after GitHub has saved the notes.
- iOS: `ios/scripts/package-website.mjs` packages `visitor-count.mjs` as an empty module (`withoutVisitorCount`); `ios/tests/package-website.test.mjs` and `ios/scripts/browser-smoke.mjs` check it.
